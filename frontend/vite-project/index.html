Grounded Context Without Replication: The Zero-Copy AI Agent

Published by Meldra AI Architecture Team · 7 Min Read

Enterprise AI agents frequently fail in production due to a lack of precise business context. Large Language Models (LLMs) cannot accurately answer queries like "What is our outstanding liability for Vendor A?" if they cannot securely inspect raw schemas, active transaction snapshops, and double-entry mappings.

Traditional data warehouses like Snowflake (with features like Cortex Sense) and Databricks address this by building proprietary semantic search indexes. However, this model has a major flaw: it requires data replication. To ground the AI, you must first build complex ETL pipelines to extract your ERP records (such as SAP BSEG tables) and ingest them into their proprietary cloud systems, paying heavy compute and storage fees along the way.

The Meldra Approach: Grounding-in-Place

meldra.ai solves the context gap without moving a single byte of data. By leveraging open-standard Apache Iceberg metadata and serverless compiles, our agents gain semantic context directly from your raw data lake.

3. DuckDB-Powered Serverless Compilation

We compile natural language queries directly into optimized DuckDB operations that target raw S3 Parquet partitions. This bypasses the heavy compute clusters, keeping your monthly infrastructure cost serverless and highly performant.

Fintech & Compliance

Real-Time Financial Audit Loop Detection via Serverless Graphs

Published by Meldra Financial Systems Team · 7 Min Read

The Business Problem: Financial audit teams and compliance officers face a significant bottleneck when inspecting transaction ledgers (like SAP's BSEG general ledger table, BKPF headers, and sub-ledgers). In modern multi-entity corporations, identifying transaction anomalies—specifically **circular transaction loops** designed to inflate book revenues or hide embezzled payments—requires looking at relationships between thousands of accounts.

Using traditional relational SQL warehouses, searching for loops requires complex recursive Common Table Expressions (CTEs) or deep nested `JOIN` queries. As ledger sizes grow, these queries either run for hours on massive compute clusters or crash due to memory exhaustion. This makes real-time compliance checking impossible.

The Meldra Solution: Hybrid Lake-Graph Architecture

We stream ledger updates directly to **S3 Apache Iceberg** for durable storage. In parallel, a background sync pipeline writes transaction edges (`TRANSFERS`) between account vertices (`Account`) inside a **Postgres AGE Relational Graph**.

Autonomous Agentic Audit Protocols

Instead of relying on manual audit batches, an **Agentic Protocol** constantly monitors the incoming transaction stream. The compliance agent executes lightweight recursive Cypher queries on the Postgres graph to search for loops and reconcile double-entry paths automatically: 

-- Query to detect circular financial loops (3 to 6 hops deep)
SELECT * FROM cypher('finance_graph', $$
  MATCH path = (a:Account)-[:TRANSFERS*3..6]->(a)
  WHERE a.status = 'active'
  RETURN path
$$) as (path gtype);

When a loop is detected, the agent immediately initiates an **A2A (Application-to-Application)** webhook, placing a temporary holds flag on the target accounts in the ERP ledger database and alerting the internal auditing team. This cuts audit latency from **30 days to sub-second real-time detection**.

Supply Chain

Eliminating Supply Chain Silos: Real-Time CDC & O2C Lineage

Published by Meldra Logistics Team · 8 Min Read

The Business Problem: Modern supply chains suffer from disjointed operational data. Inbound logistics, warehouse inventory ledgers, and customer Order-to-Cash (O2C) records reside in completely separate databases.

When unexpected disruptions occur (e.g. stockouts, shipping delays, customs blocks), inventory planners are blind. Because joining these tables requires extracting data from legacy ERP logs, stockout alerts are usually delayed by **12 to 24 hours**, resulting in missed order deadlines, customer cancellations, and chargebacks.

Real-Time CDC Ingestion with Serverless Compiles

Meldra.ai implements lightweight Change Data Capture (CDC) pipelines. Instead of spinning up permanent Spark processing nodes to ingest stream partitions, we write transaction changes directly to S3. Meldra compiles these incremental logs on-the-fly using DuckDB: 

-- Incremental Merge of warehouse stock changes into S3 Iceberg
MERGE INTO inventory_catalog.default.stock_levels t
USING (SELECT * FROM read_parquet('s3://warehouse-cdc/delta/*.parquet')) s
ON t.sku_id = s.sku_id
WHEN MATCHED THEN UPDATE SET t.quantity = s.quantity, t.last_updated = s.event_time
WHEN NOT MATCHED THEN INSERT (sku_id, quantity, last_updated) VALUES (s.sku_id, s.quantity, s.event_time);

Automated A2A Procurement Triggers

Our agentic protocol monitors these serverless merges. If an inventory merge indicates that stock levels for a critical part drop below safety limits, the agent runs a dependency scan on the S3 graph of suppliers.

It automatically invokes a secure **A2A API webhook** directly back into your ERP's procurement module (e.g., SAP Material Management), drafting a Purchase Requisition (PR) to replenish stock from the fastest supplier, completely bypassing manual procurement delays.

Zero-Trust Employee Lifecycle Sync via SuccessFactors Agentic Protocols

Published by Meldra Identity Architecture Team · 7 Min Read

The Business Problem: Employee role changes and system onboarding represent a massive operational security risk. When an employee is hired, changes departments, or is terminated in **SAP SuccessFactors**, these changes must immediately propagate to downstream directories, financial ledgers, and identity access managers.

Typically, this synchronization is handled by manual spreadsheets or batch schedules that run overnight. During the latency window, former employees can retain access to sensitive financial environments (zombie accounts), representing a severe compliance breach under SOC2 and SOX.

Serverless IAM Audit Mappings

Meldra streams SuccessFactors event logs into the central `employees` Iceberg table on S3, mapping current role descriptors to organizational trees inside the Postgres graph database. This lets security agents execute instant graph sweeps: 

-- Scan to identify access privileges mismatching the HR organizational tree
SELECT * FROM cypher('org_graph', $$
  MATCH (e:Employee)-[:ASSIGNED_TO]->(r:Role)
  MATCH (e)-[:MEMBER_OF]->(d:Department)
  WHERE r.tier > d.max_allowed_tier
  RETURN e.name, r.name, d.name
$$) as (emp_name gtype, role_name gtype, dept_name gtype);

Zero-Trust A2A Access Provisioning

The **Agentic Protocol** acts as an autonomous administrator. The moment a role change event updates S3, the agent detects department changes (e.g. Sales to Finance), maps the allowed system permissions, and executes automated **A2A API callbacks** to the IAM provider.

It immediately revokes the old tokens, provisions the new corporate credentials, and logs the entire action in the **Audit Timeline**, guaranteeing absolute security compliance in less than **2 seconds** from the initial HR action.

SOX & SOC2 Audit Trail MCP: Every Agent Action Becomes an Immutable Log

Meldra Compliance Engineering · 8 Min Read · MCP Scenario #4
Scenario: Financial services firms under SOX Section 404 must maintain an immutable, timestamped record of every data access, table modification, and agentic decision that touches financial records. Traditional logs stored in mutable databases fail audits because they can be altered.

The MCP Design: Every tool invocation through the Meldra MCP server automatically fires a log_audit_event side-effect. This writes an immutable, append-only record to an S3 Iceberg partition with snapshot isolation — meaning the log itself can never be retroactively altered, deleted, or overwritten.

# Audit MCP interceptor — fires on every tool call
@mcp_tool_middleware
async def audit_interceptor(tool_name, args, user_id, result):
    await write_iceberg_audit(
        table="compliance.audit_log",
        record={
            "event_id":    str(uuid4()),
            "timestamp":   datetime.utcnow().isoformat(),
            "user_id":     user_id,
            "tool":        tool_name,
            "args_hash":   sha256(json.dumps(args)).hexdigest(),
            "result_hash": sha256(str(result)).hexdigest(),
            "outcome":     "success" if result else "failure"
        }
    )
    # Iceberg's snapshot isolation guarantees immutability

During a SOX audit, the compliance team runs a simple MCP query: "Show me all financial table modifications in Q3 by user svc-etl-agent." The agent scans the Iceberg audit partition and returns a structured, verifiable log — ready for the external auditor's review.

MCP · Risk & Fraud

Fraud Ring Detection MCP: Graph Traversal Catches Payment Collusion in Milliseconds

Meldra Financial Crime Unit · 10 Min Read · MCP Scenario #7
Scenario: A multinational bank processes 4 million inter-bank payment instructions per day. Fraud analysts need to detect payment ring schemes — where groups of seemingly unrelated accounts circulate funds to create artificial transaction histories before executing a large withdrawal. Traditional rule-based systems miss these patterns because they require multi-hop relationship traversal across the full payment graph, which is computationally prohibitive in SQL.

The MCP Design: Meldra's Fraud Detection MCP Server exposes a detect_payment_rings tool that triggers a recursive Cypher graph traversal in the Postgres AGE transaction graph. It checks every incoming payment batch for loops of 3–8 hops, flagging any cycle above a configurable velocity threshold.

-- Fraud Ring Detection Cypher Query (executed via MCP tool)
SELECT * FROM cypher('payments_graph', $$
  MATCH cycle = (a:Account)-[:SENT_TO*3..8]->(a)
  WHERE ALL(r IN relationships(cycle)
    WHERE r.amount > 10000
    AND r.timestamp > NOW() - INTERVAL '24 hours'
  )
  WITH a, cycle, length(cycle) AS hops
  WHERE hops >= 3
  RETURN a.account_id, hops, [n IN nodes(cycle) | n.account_id] AS ring_members
  ORDER BY hops DESC
$$) as (account_id gtype, hops gtype, ring_members gtype);

# When a ring is found, the MCP agent auto-escalates:
mcp.invoke("freeze_accounts",       {"account_ids": ring_members})
mcp.invoke("notify_fraud_team",      {"severity": "CRITICAL", "ring": ring_members})
mcp.invoke("log_sar_filing_request", {"ring": ring_members, "evidence": cycle})

The full detection-to-freeze pipeline runs in under 200ms per batch — making real-time payment block feasible at scale. Traditional BSS/OSS fraud systems running on nightly batch reports would have missed the same ring until the next business day.

Welcome to the Meldra.py interactive training guide! This curriculum walks you through the step-by-step process of building, running, and managing zero-copy pipelines in the application.

Module 1: Create a Lakehouse Connection (Local vs. Cloud)

First, set up your target environment. Navigate to the Workspace tab:

  • AWS S3 & Glue Setup: Select "Amazon AWS" and enter your target S3 Bucket URI (e.g. s3://meldra-lakehouse-warehouse/), region, and connection keys.
  • GCP GCS & BigLake Setup: Select "Google GCP" and configure your target GCS Bucket URI and BigLake Service credentials.
  • Click Apply Connection Parameters.

Module 2: Ingestion & Table Creation

Navigate to the Ingest tab to create tables from raw sources:

  • Upload or drag-and-drop a CSV file (e.g. employees.csv).
  • Specify the target namespace (e.g., default) and Table Name.
  • Choose Ingestion Write Mode: Append (add new records) or Merge (upsert based on a unique key).
  • Click Start Ingestion Pipeline.

Module 3: Data Studio SQL Queries & Schema Evolution

Navigate to the Data Studio tab. You will see your newly created tables in the left sidebar catalog:

  • SQL Console: Select a table, write standard ANSI SQL queries, and click Run Query to review real-time outputs in-memory.
  • Schema Evolution: Click "Schema Evolution" subtab to add new columns, rename existing headers, or delete outdated fields as instant zero-copy metadata operations.

Module 4: Establishing Data Quality Contracts

Prevent database anomalies and schema drift. Navigate to the Data Quality subtab:

  • Click "Add Validation Constraint" to add a rule.
  • For example, choose column salary, constraint Greater Than Or Equal (>=), value 0.
  • Click Save Rules. Future ingestions will validate rows against these rules automatically.

Module 5: Automating Pipelines with Airflow

To run daily maintenance consolidations at scale, navigate to the Workspace tab:

  • Click the GCP or AWS provider selector.
  • The **Airflow DAG Exporter** automatically updates to output a scheduling template.
